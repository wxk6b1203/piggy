# 05 · 性能与资源优化专章（内存 / CPU / GPU）

> 上游：[01-architecture.md](01-architecture.md)、[04-frontend-design.md](04-frontend-design.md)、[02-pi-rpc-integration.md](02-pi-rpc-integration.md)

性能是 Piggy 的一等需求（00 G3/G4），不是事后调优。本文给出：预算表（§2）、每条预算对应的机制（§3–§5）、测量与回归方法（§6）。

## 1. 资源画像（现实约束）

| 项 | 量级 | 来源 |
|---|---|---|
| pi worker（Node 进程） | 空闲 RSS ≈ 60–120MB，流式中峰值更高 | Node 运行时 + 会话状态 + 扩展 |
| WebView 基线 | ≈ 60–120MB（平台相关） | 系统 WebView |
| 事件速率 | `message_update` 可达数百~数千条/秒（逐 token） | 协议 §4.2 |
| 长会话 | 数千消息、单消息可含大 diff/长输出 | session-format |

结论：**最大内存变量 = 活跃 worker 数量；最大 CPU 变量 = 事件处理路径上的每条开销**。两者都必须被结构性约束，而非尽力而为。

## 3. CPU：事件路径削减

### 3.1 零轮询架构

- 一切状态由事件驱动（pi 事件 / fs watcher / 状态机迁移）；**禁止任何 `setInterval` 轮询**（前端 lint 禁用、Rust 侧评审清单）；
- 唯一周期任务：空闲回收计时器（每 60s 一 tick，O(worker 数)）。

### 3.2 Rust 合帧器（第一道削峰）

见 03 §2.6。关键决策与理由：

- **delta 合并、非 delta 直通**：`text_delta` 类是高频小载荷，合并无信息损失（顺序保持）；生命周期类事件低频且驱动状态迁移，合并反而增加延迟与语义风险；
- **16ms 窗口**：对齐显示帧率；窗口内的多个 delta 拼接为单帧字符串（`String` push，一次 IPC 序列化）；
- **块边界立即冲刷**：`text_end`/`toolcall_end` 等边界事件触发冲刷，避免"块已结束但文本还压在帧里"的视觉滞后；
- **效果**：IPC 消息量从 token 速率（N 千/s）降到 ≤60/s；JSON 序列化次数同比例下降；前端事件循环压力与输出速率解耦。

### 3.3 前端瞬态通道（第二道）

04 §4：帧 → `applyFrame` → 写进**流式那一行**的 `live` 槽位。要点重申（CPU 视角）：

- 订阅面只有那一行（行组件选自己那一行的切片，immer 让其余行引用不变）→ 转录本体与
  虚拟化器**不重渲染**（`ids` 的身份只在结构变化时变）；
- 槽位里是字符串追加，块边界（`*_start`）才建节点 → 没有 DOM 重建；
- zod 只校验 envelope（类型判别字段），不深扫文本载荷。

（2026-09-24 之前这里是"无 React 渲染参与 + `appendData` 原地追加"的 DOM 直写通道；
它带来的三个结构性错误见 04 §3.2 —— 单帧省下的那点 reconciliation 远不值那个代价。）

### 3.4 React Compiler

- 全组件自动 memoization；配合 zustand selector 订阅，消息提交只渲染受影响行；
- 转录行组件保持"输入少而稳"（协议对象引用稳定 + UI 态分离），让编译器跳过率最大化。

### 3.5 Markdown 预算

- **流式**：增量解析，每帧只 lex 最后 1~2 个块（尾部 ≈11 µs/次 vs 全文 ≈541 µs/次），
  冻结块连 React 元素一起复用；**转正**：整段解析一次（04 §5.1）；
- 流式中的围栏代码块**不上色**、不自动折叠（`CodeBlock` 的 `streaming`）——
  内容每帧都在长，shiki 每帧重跑是这条链上最贵的一步；
- Shiki 语言包 LRU ≤ 16、可视区外不高亮（04 §5.2）——Shiki 完整包是前端最大的可选依赖，绝不全量打包。

## 4. 内存：worker 与数据治理

### 4.1 空闲回收（最有效的一条）

worker 空闲（`agent_settled` 后）超过 `idleTimeout`（默认 10min，可配 0=永不）→ 优雅退出；tab 保留（transcript 由 store 渲染，无需 worker）。再次交互时 respawn + `switch_session` + 游标补齐（02 §7.5）。**后台标签页不加速回收**（保证挂起的 Fleet 任务完整），但用户可手动"休眠标签"。

### 4.2 并发上限

`maxWorkers` 默认 8（可配）。超限时打开新 tab → 提示并建议回收最闲 worker（一键执行）。Fleet 任务同样计入上限（06 §3.4）。

### 4.3 标签页内存策略

- 非活动 tab：DOM 卸载（Workspace 按 tab 条件渲染），store 数据保留（消息为紧凑协议对象，1 万条 ≈ 数十 MB 内）；
- "休眠标签"操作：丢弃 store 中的消息数据（保留会话文件指针 + 游标），激活时 `get_messages` 重建——内存换取秒级恢复的选择权交给用户。

### 4.4 数据结构纪律

- messagesStore normalized（03 §3.2），共享引用而非拷贝；
- Rust pending map、环形 stderr 缓冲、合帧缓冲全部有界；
- 不缓存 `get_tree` 全树超过最近 2 个会话（LRU）。

### 4.5 大载荷

- bash 截断输出、diff、图片：协议侧已含截断语义（`truncated`/`fullOutputPath`，02 §3.2）；GUI 永远不把 >64KB 文本塞进 DOM（折叠 + 按需读文件）。

## 5. GPU 与渲染合成

### 5.1 合成器友好

- 动画/交互反馈只动 `transform` 与 `opacity`（04 §9 红线）；侧栏折叠、面板滑入、Toast 均如此；
- 滚动条自绘（overlay，`transform` 定位），不引入模拟滚动库；
- 流式光标闪烁用 CSS `steps()` 动画（合成器驱动，无 JS）。

### 5.2 绘制面积控制

- 转录行 `content-visibility: auto` + `contain-intrinsic-size`（离屏行跳过 layout/paint）；
- 虚拟化窗口 overscan 有限（前后各 6 行）；
- 主题色一律 CSS 变量（换主题零重绘重排）；antd v6 默认 CSS 变量模式 + `hashed:false`，Modal/Drawer mask blur 保持关闭（04 §6）。

### 5.3 WebView 配置

- macOS：`transparent: false`（合成器直通，避免每帧透明混合）；标题栏 `titleBarStyle: Overlay`；
- Windows：WebView2 默认 GPU 管线，`disable_web_security` 等危险项一律不碰；
- Linux：禁用 `WEBKIT_DISABLE_COMPOSITING_MODE` 相关 workaround 的自动注入，按发行版白名单处理。

### 5.4 能耗

- 无动画空闲态零重绘（DevTools performance 面板验证：无 rAF 待续、无定时器）；
- 空闲回收直接消灭 Node 进程空转（对笔记本电池友好——这也是选 Tauri 的动因之一，01 §3.1）。

### 5.5 编辑器与重资产分块

- Monaco 全家（core+59 个编辑器贡献+workers+选定语言）为独立异步 chunk，首次打开预览/设置/diff 才加载：chunk ≤ 2MB gzip（2026-09-24 实测 ≈ 1.2MB gzip：editor.api 697 + monaco-setup/贡献 307 + workers ~200），加载后 RSS 增量 ≤ 60MB，未加载时 = 0（10 §2.2–2.3）；MonacoHost 单例工厂 + 实例池（**可见才创建 + LRU 保留水位 6**，见 10 §2.3 —— 每实例实测 ~0.5–1.5MB / ~70ms，真正要防的是「标签数量把实例数堆起来」）；
- Shiki 语言包 LRU 策略不变（§3.5）；聊天内嵌 diff 用自绘轻渲染，不实例化 Monaco（10 §2.1）；
- xterm.js 实例仅在终端面板可见时挂载，隐藏即 `dispose`（10 §4）。

## 5.6 「打开会话的 1 秒」花在哪（2026-09-23 实测）

起因（用户问）："点击打开会话，要大概 1s 才能加载出来，长会话就更加长，
是 pi 必须存在的加载时间，还是说我们的 UI 有什么问题？"

答案：**绝大部分是 pi 自己的启动，而且主要是"你装的扩展"**；我们这边可省的一笔（73 ms）
当日已挪到后台。逐段实测（本机、macOS、最大会话 11.13 MB；工具：
`pnpm --filter @piggy/desktop pi:cost`，可复现）：

| 段 | 实测 | 谁的 |
|---|---|---|
| node + pi 核心启动（`-ne`，零扩展） | **≈ 214 ms** | pi（地板） |
| + **pi-subagents**（14 MB） | **+431 ms** | 用户装的扩展 |
| + pi-web-access（8.5 MB） | +32 ms | 用户装的扩展 |
| + pi-todo / pi-guardrails（TS，经 jiti 编译） | +50 / +55 ms | 用户装的扩展（本地目录） |
| 上面合计：`pi --mode rpc` 起来并答出 `get_state` | **≈ 744 ms** | pi |
| + 我们注入的 `piggy-bridge` + 守卫 | **+12 ms** | 我们（几乎不花钱） |
| + 会话文件本身（11.13 MB vs 0.14 MB 之差） | **+50 ms** | pi（解析 JSONL） |
| 我们的游标初始化 `get_entries(None)` | **+74 ms**（回包 10.90 MB / 1069 条） | **我们 —— 已修**：挪到后台 |
| 我们的尾页 `session_page` + 轮廓 `session_outline` | +15.5 / +8.8 ms | 我们（Rust 直读文件，已是最优） |
| 前端：store → 面板 → 首屏渲染 | ≈ 50~100 ms | 我们 |

三条结论：

1. **"长会话更慢"里属于我们的只有一项**：`get_entries` 不带 `since` 时 pi 会把**整段**
   会话发回来（`rpc-mode.js` 的 get_entries 分支），而我们只要里面的 `leafId` ——
   11 MB 会话 74 ms，随会话线性增长。现在 `create_tab` 不再等它：
   `spawn_cursor_init` 在后台补（游标只是崩溃恢复的优化，见 03 §2.7）。
   文件本身反而很便宜：11.13 MB 对 0.14 MB 只差 50 ms。
2. **扩展是启动时间的大头，而那是用户的配置，不是 Piggy 的策略**（规矩 95b 的同一立场）：
   我们**不会**为了快而替用户 `-ne` 掉扩展（那会让工具凭空消失）。要快只有两条路：
   用户按需卸载/停用重的扩展，或者我们做**预热进程池**（见 §5.7）。
3. 我们注入的扩展与 Rust 数据面几乎不占时间（+12 ms / +25 ms 量级），
   所以"是不是我们的 UI 有问题"——**不是**；UI 那一段是 50~100 ms。

## 5.6b 2026-10-09 复测：同一台机器、pi 1.1.0

| 段 | 09-23 | 10-09 | 备注 |
|---|---|---|---|
| ① pi 裸启动（`-ne`） | 214 ms | **225 ms** | 地板 |
| ② + 用户已装扩展 | 744 ms | **540 ms** | 扩展贡献 315 ms（pi-subagents +129、pi-init +4、pi-web-access +31 …） |
| ③ + 我们的 bridge | — | 502 ms | **我们注入的扩展几乎不花钱** |
| ④ + 守卫 | — | 482 ms | 同上 |
| ⑤ 起进程 + `get_state`（含 11 MB 会话） | — | **527 ms** | 这一笔就是"点一下要等"的全部 |
| ⑥ 我们的游标初始化 | 74 ms | 81 ms | 已在后台，不挡打开 |

热态命令（同一个进程里再发一次）：`get_state` 2 ms、`get_available_models` 2 ms、

这解释了为什么"第一个会话"和"之后的会话"手感不同（每个会话一个独立进程）。

## 5.6c 已经做的两笔（2026-10-09）

1. **第一帧反馈**（乐观 UI）：点击后**立刻**画出「正在启动 pi…」占位标签
   （门禁第 29 段实测 **13.7 ms** 出现，而 mock 的 `tab_create` 是 250 ms），
   `tab_create` 回来时换成真面板。**感知等待 ≈ 0**，真机总时长不变。
   实现要点：占位面板 id 前缀 `session:pending:`（同一份"要打开的会话"只允许一个占位）、
   换面板时先加真面板再关占位、`persist()` 会把占位从布局 JSON 里剔掉
   （否则重启后会多一个「会话文件不存在」的僵尸标签）。
2. **握手不再持 registry 锁**：`create_tab` 拆成「锁内 spawn → **锁外握手** → 锁内记账」
   （§5.6 里 527 ms 的等待，以前是握着全局锁等的 —— 别的标签页的命令会一起卡住）。
   契约用例 C15 量这条：建 tab 期间别的命令抢锁最久等 **1.2 ms**（改造前红检 480 ms）。

## 5.7 预热 worker：**已删**（2026-10-13；机制与开关一起删）

> **2026-10-13 决策：整条功能删掉**（用户"感觉没什么用、时间上还是大差不差"之后拍板）。
> 依据是**在 Windows 真机上第一次量到了收益**，以及量完之后看它落在哪一段：
>
> ① **收益是真的，而且比估计大**：C16 在 Windows 上连跑 6 次 ——
> 复用打开 **218 / 858 / 389 / 259 / 258 / 247 ms** vs 冷启动
> **1253 / 2028 / 2491 / 2195 / 1313 / 1204 ms** → **每次省 1.0–2.1 s**
> （注：早先"Windows 冷启动 2.2 s"那个数是**剥 cmd 垫片之前**测的，剥掉之后是 1.2–2.5 s，
> 借来的那部分不是预热省的）。
>
> ② **但它省在一个已经被遮住的窗口里**，而且**每次启动的第一个会话永远吃不到**：
> 预热池是在 `create_tab` **之后**才补位的（那时才知道用户在哪个目录工作），所以
> 启动 → 开第一个会话必然是冷启动（等 1.2–2.5 s）→ 补位本身还要 1.2–1.8 s（实测就绪耗时）
> → 10 分钟保鲜期。**"开一个会话就干活"的用法永远命中不到**，只有"十分钟内开第二个"才吃到。
> 而"打开会话"这一段本来就被乐观 UI 占位遮住（13.7 ms 出第一帧，§5.6c 第 1 笔）——
> 这与 2026-10-10 关掉 macOS 那条用的是**同一把尺子**：
> **省下的时间必须大于用户能感知到的等待，被占位遮住的等待不算收益。**
>
> ③ **代价是硬的**：常驻一个 pi 进程（实测 RSS 173→199 MB 空载、256 MB 切完会话），
> 外加一条"进程池 + 会话切换"的复杂度（判据、保鲜期、补位、回收、`boot_reset` 收割）。
>
> 结论：**1–2 s 落在被遮住的窗口里、还只对"十分钟内的第二个会话"生效，不值 200 MB + 这条复杂度。**
> 删除范围：`Registry.warm` / `Warm` / `WARM_TTL` / `spawn_warm` / `adopt_warm` / `take_warm` /
> `warm_matches` / `should_refill_warm` / `take_expired_warm` / `take_warm_for_shutdown`、
> 配置字段 `warm_worker` 与下发字段 `warmWorkerSupported`、设置页那一行、
> 契约用例 C16、以及为 C16 才存在的 `ConfigDirGuard`（测试专用配置目录覆盖）。
> ⚠️ **`TabSlot` 共享槽与 `coalesce.rs::frames_follow_a_rebind` 保留**：那条不变量
> （"帧的通道名在 flush 时读、不在构造时拷"）与预热无关，坏了就是静默串台。
> 本节的其余内容**按原样留档** —— 它是这次删除决策的依据，不是现状描述。


> **2026-10-10 决策：macOS 不再提供这个能力**（用户实测"开了还是要等"后拍板）。
> 判据是**"省下的时间必须大于用户能感知到的等待"**，而这里两条都不满足：
>
> | 量 | 实测（`pi 1.1.0`、macOS，本机 3 次） |
> |---|---|
> | 复用打开 vs 冷启动 | **37 / 38 / 40 ms vs 483 / 505 / 484 ms**（省 443–474 ms） |
> | 这笔省在**哪一段** | **只省"打开会话"**。那一段已被乐观 UI 占位遮住（13.7 ms 出第一帧，§5.6c 第 1 笔）→ 感知不到 |
> | "发第一条消息" | **一点没省**：冷启动到出答案 5.3 s，其中 pi 启动只占 ~470 ms（`switch_session` 会重建 runtime，实测首次切 11 MB 会话 258 ms、第二次 68 ms） |
> | 代价 | 常驻一个 pi 进程：实测 RSS **173 MB（握手完成）→ 199 MB（空闲）→ 256 MB（切完会话）** |
>
> 结论：**拿 200 MB 常驻换一个看不见的 450 ms 不划算**。闸门是
> `config::app::warm_worker_supported()`（macOS 恒 false），只装在**补位那一个使用点**上
> （`registry.rs::should_refill_warm`）—— 刻意**不在 `clamp()` 里改 `warm_worker`**：
> 那是持久化值，改了就等于把用户（或从 Windows 同步过来的）设置悄悄写坏。
> 平台判据只此一份，设置页由后端 `perf_config_get` 下发的 `warmWorkerSupported` 决定显不显示。
> 机制本身**不删**：Windows 才可能有感（三层 cmd 垫片 + Defender），那边开关照旧。

**Windows 上的收益仍未量到**（`docs/05` 一直承认这一点）：只有在 Windows 真机上量到
before/after ≥1 s 量级，才谈得上"要不要在那边默认开"。注意 `pi/process.rs` 的
`direct_command` 已经剥掉了一层 cmd 垫片，真实收益可能低于"2.2 s"的估计。

**历史实测**（2026-10-09，`pi 1.1.0`、macOS，契约用例 C16 直接量）：
同一个 cwd、同一档位下打开一个**新会话** —— **复用预热进程 38 ms vs 冷启动 503 ms（省 464 ms）**；
换到 11 MB 的既有会话是 208 ms（那一笔含 pi 解析会话文件，且那是"新会话"场景下的数，
2026-10-10 复测同一件事是 258 ms）。
**代价**：一个常驻 pi 进程，空载实测 **RSS 206 MB**；保鲜期 10 分钟，
心跳（`lib.rs` 的 60s tick）会把它回收掉，`boot_reset` 也会收（它不属于任何 tab）。

为什么当初仍然**默认关**：+206 MB 常驻是"用户没要求过的资源占用"，
而"点了没反应"那一笔已经由乐观 UI 解决（§5.6c）；真正的收益在 Windows
（三层 cmd 垫片 + Defender，冷启动 2.2 s）—— 那台机器上量到之后再决定要不要默认开。

⚠️ **两处曾经的错误说法（2026-10-10 审计修正）**：
1. 「复用**进程**就等于扩展加载免单」是**不对**的：`switch_session` 会重建 runtime
   （又一次 resource loader reload + 会话文件解析），省掉的只是"进程启动 + **首次** import"。
   实测边界很清楚：同进程**第一次**切 11 MB 会话 258 ms、**第二次** 68 ms。
2. **`idle_timeout_min = 0` 曾把预热的过期回收一起短路掉**（`lib.rs` 的 `continue` 排在
   `take_expired_warm()` 前面）—— 而 `0` 的语义是"**tab** 永不回收"，与预热无关。
   现象：白挂一个 200 MB 的 pi 几小时，而设置页那句"超过 10 分钟没用会被换掉"是假的。
   已修：预热的过期判定移到 `continue` **之前**（2026-10-10）。

⚠️ 复用还有一个**权限**副作用（不属于性能，见 docs/17 §2.2c 末段）：
「工作区内修改」档的写边界本来是 spawn 时写死的，复用会让它停留在旧项目 —— 已修。

判据（`sessions/registry.rs::warm_matches`，纯函数 + 11 条断言）：
**档位一致**（`--tools`/`-e` 是 CLI 参数，换档等于换能力）、
**在保鲜期内**、**cwd 一致 —— 仅当目标会话没有 cwd 头时**（预创建的空文件、`--no-session`；
pi 的 `SessionManager.open` 对没有 header 的文件用**进程 cwd** 兜底；
已有会话的文件头里有 cwd，`switch_session` 会按头重绑，实测 `bash` 的 pwd 与项目级扩展都跟着走）。
消费失败**一律回退冷启动**（备用进程可能在这几秒里崩了）。

### 当初的犹豫（留档；**下面描述的机制已删，见本节开头**）

pi 的启动没法再压（§5.6b 的 ①～④），但**可以提前付**：应用空闲时先起一个
`pi --mode rpc --no-session` 的备用进程，用户点开会话时用 `switch_session` 指到目标文件。

**可行性已经实测**（2026-10-09，`pi 1.1.0`）：
- `--no-session` 起的 worker 上跑 `switch_session <11 MB 会话>`：**208 ms**（vs 冷启动 527 ms）；
- 换过去之后 **cwd、项目级扩展、`bash` 的工作目录都跟着会话头走**（与在新 cwd 里冷启动等价）；
- 新会话只要预创建文件里**由我们写上 pi 的会话头**（`{"type":"session","version":3,…,"cwd":…}`），
  同一个 worker 切过去 **284 ms** 就绪、pi 正常续写（`CURRENT_SESSION_VERSION=3`，低版本会自动迁移）。

代价与风险（**这些是实现时要处理的东西**）：
- 收益在 macOS 上只有 ~250 ms，而"感知等待"已经由 §5.6c 的第 1 笔解决了；
  **真正的收益在 Windows**（三层 cmd 垫片 + Defender，冷启动实测 2.2 s），但那台机器上量不到；
- 要把"一个会话一个进程"换成"进程池 + 会话切换"：worker 的 stdout reader 目前
  **把 tab_id 烧在闭包里**（`run_reader`/`FrameCoalescer`），复用一个进程就得先把
  tab_id 变成可重绑的共享状态 —— 那里的错误形式是"事件发到别的标签页"，属于静默串台；
- 还要一套生命周期：备用进程被占用/失效/权限档不匹配时回退冷启动、常驻内存上限、
  与"休眠回收"的交互。
处置：**已实现，带开关、默认关**；上面三条风险分别由"纯函数判据 + 契约用例 C16"、
"消费失败回退冷启动"、"心跳回收 + boot_reset 回收"兜住。

⚠️ **C16 必须把配置目录隔离掉（2026-10-10 修）**。补位是设计的一部分：开关为真时
`create_tab_unlocked` 在复用成功后会**就地再补一个**备用 worker（`registry.rs` 的
"补一个备用 worker（锁外、后台）"）。而那个开关来自 `~/.piggy/config.json` ——
**跑测试这台机器的活配置**。于是：用户开着 GUI（`pnpm tauri dev`）把预热开关打开并落盘，
C16 里的 `assert!(reg.warm_worker().is_none(), "备用槽应当已被消费掉")` 必然失败，
而产品行为完全正确（实测：`tab_create 复用了预热 worker` 成功、紧接着 `spawn pi [warm:…]`
补了一个新的）。修法是让用例把配置目录指向自己的临时目录
（`config::app::ConfigDirGuard`，线程本地覆盖，panic 也会还原），
于是空配置 → 开关为默认 false → 只量"复用"本身。
判据：**凡是用例会走到"读用户配置"的代码路径，就得先把配置目录隔离掉** ——
否则同一份代码在"用户开了开关"的机器上会红，而那与代码质量无关。
